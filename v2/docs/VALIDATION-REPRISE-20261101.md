## Exception reproduite et correction de l'écriture atomique

Un essai ciblé reproduit l'échec avec les mêmes EXE baseline et candidat, dans une nouvelle fixture, en session interactive 2. Un [diagnostic temporaire](evidence/20261101/windows-update-hook-diagnostic/) capture les types, HRESULT et méthodes de pile, sans message d'exception, arguments, variables d'environnement ou dump mémoire. Il est chargé seulement dans le helper de cette copie de test. Son fonctionnement est d'abord vérifié sur un petit exécutable autonome synthétique ; les EXE Pesto restent inchangés. Cet essai instrumenté ne qualifie pas la livraison.

Le diagnostic relève `UnauthorizedAccessException`, HRESULT `80070005`, dans `FileSystem.MoveFile`, puis `UpdatePackage.WriteAtomic`, `UpdateTransaction.Save` et `ExecuteCoreAsync`. Deux refus rapprochés précèdent la propagation : l'écriture de récupération échoue aussi. Le journal reste `backedUp`. L'identité du helper arrêté est vérifiée et la tâche temporaire est retirée. Les empreintes des 18 fichiers collectés correspondent aux originaux distants ; les sources du diagnostic sont également conservées.

Un programme minimal sur ce Windows 11 reproduit le refus de `File.Move(..., overwrite: true)` lorsqu'un lecteur garde le fichier ouvert, même avec `FileShare.ReadWrite | FileShare.Delete`. Après fermeture du lecteur, le remplacement réussit. `File.Replace` réussit dans cette expérience, mais n'est pas introduit dans le correctif : la méthode de publication existante est conservée. Le [signalement primaire .NET 114230](https://github.com/dotnet/runtime/issues/114230) décrit également cette classe de refus. L'identité du processus qui retenait le journal au moment des essais Pesto n'est pas établie.

Le correctif conserve le même fichier temporaire, son écriture durable et le remplacement atomique. Sur Windows, seuls les refus de publication `5`, `32` et `33` sont réessayés, avec au plus vingt attentes de 50 ms. Un refus persistant est propagé ; aucune suppression préalable du journal ni copie de secours non atomique n'est utilisée. Les gardes contre les liens sont revérifiées avant publication. Le nettoyage d'un temporaire appartenant à l'opération ne masque plus l'erreur initiale. Le lecteur du banc ferme désormais son flux après une copie mémoire bornée à 256 Kio, avant l'analyse JSON. Cela réduit la durée pendant laquelle il retient le fichier ; cela ne répare pas rétroactivement le helper du baseline.

Les propositions Spark sont relues et corrigées avant intégration : `UnauthorizedAccessException` n'a pas de propriété `NativeErrorCode`, un `using var` en tête de méthode ne ferme pas le flux avant le retour, et les tests proposés ne synchronisaient pas correctement le verrou. La validation [sur Windows avec le SDK 10.0.302](evidence/20261101/windows-atomic-write-targeted/) passe **3/3** tests d'écriture réelle, **25/25** tests de mise à jour et **60/60** contrôles du banc. Les deux projets compilent sans avertissement ni erreur. Ces résultats portent sur l'archive source identifiée et ses quatre modifications locales, avant commit ; ils ne remplacent pas la campagne complète du prochain commit.

Le [nouvel essai natif ciblé](evidence/20261101/windows-reader-health-targeted/) réussit avec ce lecteur corrigé et les EXE d'origine, **sans StartupHook**. Il conserve les deux reçus de santé : refus du candidat synthétiquement défectueux, puis restauration et démarrage confirmé de l'ancien programme. Le statut final est `rolledBack`, les empreintes de l'installation et du runtime reviennent exactement à celles du baseline, et le profil sentinelle est inchangé. Les vingt fichiers sont vérifiés contre leurs empreintes distantes, puis la tâche temporaire est retirée. Il reste 25,79 Go libres sur le portable. Cet essai d'un seul scénario ne qualifie ni les ZIP de la prochaine compilation ni toute la campagne.
